# M5.3 Evaluation Report

## 1. Objective

M5.3 把 M5.2 的 failure-aware knowledge retrieval 接入**失败分支的运行时**：
任务在 observe/plan/execute 任一阶段失败后，用 `errors.classify()` 得到的失败
上下文做一次**诊断型 retrieval**，并把结果落成 additive 产物
`failure_retrieval.json`（`backend/app/rag/failure.py`）。

M5.3 明确不做的事：

- 不是自动修复：不修改 `repair.py` 的策略，不扩大可修复错误集合；
- 不是重新规划：不调用第二次 LLM，不重新生成计划；
- 不是重新观察：复用内存中已有的脱敏摘要；
- 不参与执行或修复决策：诊断结果是**只读证据**，不回灌规划与修复。

本报告只声明：**在受控 fixture 上验证运行时失败检索的确定性、可解释性、
安全一致性与契约不可变性**，不声明任何系统成功率的普遍提升。

## 2. Architecture

失败分支的数据流（全部确定性，无模型调用）：

```
失败异常
   │
   ▼
errors.classify()                    # 唯一权威：code -> category / phase
   │
   ▼
failure.build_failure_context()      # 投影为 failure_context（调用方不可伪造）
   │
   ▼
retrieval.retrieve(summaries, failure_context=...)
   │                                 # 复用 memory 中已脱敏 summaries
   ▼
failure.build_failure_retrieval()    # 组装 advisory 产物
   │
   ▼
failure_retrieval.json               # additive；不回写 plan / repair / retrieval
```

- **single source of truth**：`errors.SPECS`。`classify()` 只信任异常的
  `code` 属性，category/phase 全部来自注册表；调用方传入的任何
  `category`/`phase` 属性都会被忽略。
- **advisory only**：`failure.py` 只读 `..pipeline.errors`，不导入
  execution / gateway / repair 驱动，也不调用模型。
- **fail-closed**：`UNCLASSIFIED` 失败（含任意未注册异常）不产出诊断产物。
- **RAG 关闭**：`rag_enabled=False` 时不产出诊断产物。

## 3. Evaluation Design

评估为 **A/B/C/D 四组消融**，同一 query 集、同一 corpus：

| 组 | 路径 | gate | knowledge |
|---|---|---|---|
| A: BM25 only | retrieval 层 | 关闭 | 关闭 |
| B: BM25 + feature gate | retrieval 层 | 开启 | 关闭 |
| C: BM25 + feature gate + failure-aware | retrieval 层 | 开启 | 开启 |
| D: runtime failure_context -> artifact | `classify` -> `build_failure_context` -> `retrieve` -> `build_failure_retrieval` | 开启 | 开启 |

- A/B/C 复现 M5.2-C 的检索层消融；D 是 M5.3 新增轴，**走运行时投影函数**，
  `failure_context` 由 `PipelineError` 经 `errors.classify()` 得到，而非手写 dict。
- D 与 C 复用同一 corpus、同一归一化上下文，因此 D 的排序指标应与 C 逐字段一致：
  这是“运行时投影不引入新影响”的确定性证据。
- 评估位于 `tests/test_m53_failure_evaluation.py`，fixture 在测试文件内构造，
  **不写入 `cases.json`，也不写入 `benchmarks/`**。
- `evaluate()` 为确定性纯函数：同输入重复运行结果 deep-equal。

## 4. Metrics

指标定义：

- `top1_hit` / `top2_hit`：期望案例是否位于第 1 位 / 前 2 位。
- `MRR`：期望案例排名倒数的均值。
- `failure_code_hit_at_2`：查询对应 error_code 是否出现在 top-2 案例的
  `failure_modes` 中。
- `repairability_consistency`：案例声明的 `repairability` 与独立投影
  （`errors.SPECS` + `repair.APPLICABLE_ERROR_CODES` + `repair.PRE_COLLECTION_PHASES`）
  的一致率，要求 `== 1.0`。
- `unsafe_retrieval_rate`：受限类别（SECURITY / DATA_INTEGRITY / TRANSPORT /
  UNCLASSIFIED）失败下，检索结果中出现 `auto_applied` 知识案例的比例，目标 `== 0`。

受控 fixture 实测结果（`evaluate()` 直接输出）：

| group | top1_hit | top2_hit | MRR | failure_code_hit@2 | unsafe_retrieval_rate |
|---|---|---|---|---|---|
| A: BM25 only | 0.333333 | 0.333333 | 0.333333 | 0.0 | 0.0 |
| B: BM25 + feature gate | 0.333333 | 0.666667 | 0.5 | 0.0 | 0.0 |
| C: BM25 + feature gate + failure-aware | 1.0 | 1.0 | 1.0 | 1.0 | 0.0 |
| D: runtime failure_context -> artifact | 1.0 | 1.0 | 1.0 | 1.0 | 0.0 |
| `repairability_consistency` | — | — | — | — | **1.0** |

- A/B 组 `failure_code_hit@2` 为 0 是设计使然：其语料按消融**不含** `failure_modes`。
- **D == C**（逐字段相等）：运行时投影把 `(error_code, category, phase)` 规范化为与
  C 相同的失败上下文，未新增影响面。
- 全部指标来自小样本 fixture，仅用于验证确定性、可解释性与安全一致性，
  **不外推为普遍效果提升**。

## 5. Required Verifications

对应 `tests/test_m53_failure_evaluation.py`：

1. **failure_context 来源 = `errors.classify()`，不可伪造**
   - 对已注册码，`build_failure_context` 的 category/phase 等于 `SPECS`；
   - 伪造 `code='duplicate_id'` 但自称 `SECURITY/observing` 的异常，仍被判为
     `DATA_INTEGRITY/executing`；未注册 code 一律 `UNCLASSIFIED`（fail-closed）。
2. **model_calls == 1**：端到端失败任务在产出 `failure_retrieval.json` 的同时，
   `report['model_calls'] == 1`。
3. **无失败任务 M5.2 == M5.3**：成功任务产物集与 M5.2 完全一致（7 个文件），
   无 `failure_retrieval.json`，`retrieval.json` 仍为 M5.2 契约键。
4. **失败任务仅 additive**：文件集 = M5.2 失败文件集 + `failure_retrieval.json`；
   `retrieval.json` 契约键不变；`repair.json` 在 RAG 开/关下逐字节相等，且不含检索字段。
5. **安全 unsafe_retrieval_rate == 0**：SECURITY / DATA_INTEGRITY / TRANSPORT
   参数化断言受限类别过滤掉全部 `auto_applied` 案例；UNCLASSIFIED 走 fail-closed
   （无 `failure_context`、无产物）。四组指标 unsafe 均为 0.0。
6. **确定性**：端到端两次运行的 `failure_retrieval.json` 逐字节相等；
   `runtime_artifact(...)` 与 `evaluate()` 两次调用 deep-equal。
7. **声明纪律**：见第 6 节，未声明系统成功率提升；failure retrieval 为 advisory only，
   不参与 repair。

## 6. Declaration Discipline

- **不声明成功率提升**：本报告只给出受控 fixture 上的确定性、可解释性、安全一致性结论。
- **fixture 不是 benchmark**：数据在测试文件内构造，未写入 `benchmarks/`，
  也未扩展冻结数据集；`benchmarks/tasks.json` 内容哈希与 `cases.json` SHA256 均不变。
- **failure retrieval 是 advisory only**：产物仅含闭集码、策展案例 id 与哈希，
  绝无计划 / 执行字段 / URL / 凭据；不回灌规划，不触发修复。
- **不参与 repair**：`APPLICABLE_ERROR_CODES` 仍为 `{pointer_not_found}`，
  `MAX_REPAIR_ATTEMPTS` 仍为 1；`repair.json` 在 RAG 开/关下完全一致。

## 7. Safety Guarantees

- **no LLM call**：新增层为纯函数；端到端任务 `report['model_calls'] == 1`。
  `failure.py` 仅导入 `..pipeline.errors`，无 gateway / openai / httpx / requests。
- **no execution influence**：`failure.py` / `retrieval.py` / `knowledge.py` 不含
  `execute_plan` / `subprocess` / `RepairProposer` / `run_task` 等执行或修复驱动。
- **no repair policy change**：未修改 `errors.py` / `repair.py` / `execution.py` /
  `gateway.py`；repair 边界与预算不变。
- **fail-closed**：UNCLASSIFIED 失败与 RAG 关闭均不产出诊断产物。
- **backward compatible**：无失败任务产物与 M5.2 逐字段一致；冻结 v1 语料对
  `failure_context` 完全中性，`retrieval.json` 仍为 M5.2 契约键。
- **deterministic**：同输入重复运行结果 deep-equal。

## 8. Known Limitations

- 评估 fixture 规模很小，**不能证明普遍提升**；结论限于确定性与安全一致性。
- 运行时失败检索使用的是 `run.py` 内存中已有的脱敏摘要，**不重新观察**，
  因此其检索质量受首次观察样本质量约束。
- 冻结 v1 语料不含结构化知识，真实 pipeline 失败产物中 `knowledge_gate` 恒为
  inactive（`applied=False`）；v2 语料下的 gate 行为由测试注入语料验证。
- `field_mapping` 特征仍未进入真实 `retrieve`，在真实链路中恒为 `unknown`。
- 本报告为 M5.3-C 冻结证据；未声明 M6 规则 / 无 RAG / RAG 对比结论。
