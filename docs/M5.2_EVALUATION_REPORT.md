# M5.2 Evaluation Report

## 1. Objective

M5.2 提升的是 **structured failure-aware retrieval**（结构化、失败感知的案例检索），
不是自动修复，也不是执行策略增强。

失败感知层只做两件事：

- 用观测到的失败上下文（错误码 / 类别 / 阶段）对检索结果做确定性的加权或过滤；
- 把案例中声明的失败知识与 `errors.py` 的失败分类体系对齐。

它不触碰执行计划、不改变 repair policy、不新增模型调用。可修复性的**唯一权威**
仍是 `errors.SPECS` 与 `repair.py` 的策略常量。

本报告只声明：**在受控 fixture 上验证确定性、可解释性和安全一致性**，
不声明任何系统成功率的普遍提升。

## 2. Architecture

检索链路保持文本优先、全程确定性：

```
query + evidence features
        │
        ▼
   BM25Okapi              (文本相关性，主体不变)
        │
        ▼
  Feature Gate (M5.1)     (结构特征过滤 / 轻量重排)
        │
        ▼
Failure-aware Knowledge Ranking (M5.2)
        │
        ▼
   final ranking
```

- **BM25**：`backend/app/rag/retrieval.py` 的 `BM25Okapi` 打分，仍是排序主体。
- **Feature Gate (M5.1)**：`match_features()` 比较查询证据特征与案例 `features`；
  `method` 冲突属安全边界，直接过滤。
- **Failure-aware stage (M5.2)**：`failure_match()` 比较观测失败与案例
  `failure_modes` / `repairability`；受限类别失败过滤带 `auto_applied` 知识的案例。
- 结构化知识只经 `backend/app/rag/knowledge.py` 的 `knowledge.load()` 读取，
  在加载期完成 schema 与可修复性投影校验。

## 3. Evaluation Design

评估为 **A/B/C 三组消融**，同一 query、同一 corpus，只改变知识字段：

| 组 | 语料 | gate | knowledge |
|---|---|---|---|
| A: BM25 only | 去 `features`、去 `failure_modes` | 关闭 | 关闭 |
| B: BM25 + feature gate | 保留 `features`，去 `failure_modes` | 开启 | 关闭 |
| C: BM25 + feature gate + failure-aware | 保留 `features` 与 `failure_modes` | 开启 | 开启 |

- fixture 内同时包含 legacy case、`features`、`failure_modes`、`repairability` 四类字段。
- 评估位于 `tests/test_rag_failure_evaluation.py`，fixture 不写入 `cases.json`，
  也不写入 `benchmarks/`。
- `evaluate()` 为确定性纯函数：同输入重复运行结果 deep-equal。

## 4. Metrics

指标定义：

- `top1_hit` / `top2_hit`：期望案例是否位于返回结果的第 1 位 / 前 2 位。
- `MRR`：期望案例排名倒数的均值。
- `failure_code_hit_at_2`：查询指定的 error_code 是否出现在 top-2 案例的
  `failure_modes` 中。
- `repairability_consistency`：案例声明的 `repairability` 与独立投影
  （`errors.SPECS` + `repair.APPLICABLE_ERROR_CODES` + `repair.PRE_COLLECTION_PHASES`）
  的一致率，要求 `== 1.0`。
- `unsafe_retrieval_rate`：受限类别（SECURITY / DATA_INTEGRITY / TRANSPORT /
  UNCLASSIFIED）失败下，检索结果中出现 `auto_applied` 知识案例的比例，目标 `== 0`。

受控 fixture 实测结果：

| group | top1_hit | top2_hit | MRR | failure_code_hit@2 | unsafe_retrieval_rate |
|---|---|---|---|---|---|
| A: BM25 only | 0.333333 | 0.333333 | 0.333333 | 0.0 | 0.0 |
| B: BM25 + feature gate | 0.333333 | 0.666667 | 0.5 | 0.0 | 0.0 |
| C: BM25 + feature gate + failure-aware | 1.0 | 1.0 | 1.0 | 1.0 | 0.0 |
| `repairability_consistency` | — | — | — | — | **1.0** |

A/B 组的 `failure_code_hit@2` 为 0 是因为其语料按设计**不含** `failure_modes`
（消融使失败知识不可用）；只有 C 组携带该知识。该表来自小样本 fixture，
仅用于验证确定性、可解释性与安全一致性，不外推为普遍效果提升。

## 5. Safety Guarantees

- **no LLM call**：检索新增层为纯函数；端到端任务 `report['model_calls'] == 1`。
  模块无 gateway / openai / httpx / requests 依赖。
- **no execution influence**：`retrieval.py` / `knowledge.py` 不含
  `execute_plan` / `subprocess` / repair 执行逻辑；failure-aware 只影响检索排序。
- **no repair policy change**：未修改 `errors.py` / `repair.py`；
  `APPLICABLE_ERROR_CODES` 仍为 `{pointer_not_found}`，`MAX_REPAIR_ATTEMPTS` 仍为 1。
- **no benchmark mutation**：`benchmarks/tasks.json` 内容哈希与 `tasks.sha256` 不变；
  冻结 `cases.json` 的 SHA256 不变（`678f87ec…`）。
- **backward compatible**：语料无 `failure_modes` 时阶段停用，输出与 M5.1 逐字段一致；
  RAG 关闭时输出保持 legacy 5 键且 `cases == []`。
- **deterministic**：同输入两次运行结果 deep-equal。

## 6. Known Limitations

- `failure_context` **尚未接入生产 pipeline**：`run.py` 未修改，真实任务中该阶段
  当前恒为 neutral，仅在评估/测试显式传入时生效。
- 评估 fixture **不是 benchmark**：数据在测试文件内构造，未写入 `benchmarks/`，
  也未扩展冻结数据集。
- `field_mapping` **未进入真实 `retrieve`**：pipeline 未把 `fields` 传入检索，
  该特征在真实链路中恒为 `unknown`。
- **小样本不能证明普遍提升**：fixture 规模很小，仅支持确定性、可解释性与安全一致性
  的结论。
