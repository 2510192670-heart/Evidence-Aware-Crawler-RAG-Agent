# M6.1-A Independent Dataset and Scoring Contract

Status: contract candidate for human acceptance. Dataset status is `m61_a_review`,
NOT a frozen m6-v1 release. Baseline: `v0.5.5-freeze`,
`15c5678a963665412f5e68e29617ddd7469b844d`. Date: 2026-09-15.

## Purpose and scope

M6 assets evaluate the current system; they are not production knowledge.
LLM proposes. Deterministic code validates and executes.
M6.1-A implements 12 representative cases before expanding to 40 in M6.1-B.
No cloud experiments, formal evaluation runner, model-generated oracle acceptance,
production service, new pagination capability or production configuration is added.

The existing 20-task S1-S5 benchmark and production cases remain unchanged.
`evaluation/fixtures/` is the chosen fixture location; no second M6 fixture tree
is created under `tests/fixtures/`.

## Layout and trust boundaries

```text
evaluation/
  datasets/m6-v1/
    manifest.json / manifest.sha256
    families.json
    cases/       # scorer-side metadata and references; NOT planner inputs
    inputs/      # public synthetic wire responses and requested fields
    oracles/     # private scorer answers
    labels/      # private external relevance labels
  corpora/m6-v1/e1.json, e2.json, e3.json
  schemas/       # evaluation validator, canonical hashing, pure scoring, JSON schema
  fixtures/      # deterministic asset builder and pure public-input projection
```

The fixture runtime accepts a public-input object, not a case object or a dataset
path. It imports neither the scorer nor oracle files, performs no file reads, and
does not accept an oracle argument. Unknown public-input/endpoint keys and reserved
scorer metadata embedded in a response are rejected. The validator reads private
answers only to validate scorer assets; it is not part of the Agent runtime.

Only `planner_inputs(public_input)` projects requested fields and existing
`cloud_summary(Observation)` results. Oracle values, labels, case IDs, split,
family and failure/repair expectations are never copied into that representation.
This is a structural boundary, not OS access control. A future harness must preserve
it and will need its own live prompt/execution/diagnostic leakage tests.

Wire response records naturally overlap correct output records. That overlap is
not oracle leakage: the forbidden information is the answer-key metadata, expected
plan/selection, labels and future failures, not ordinary observed data.

## Case schema

The normative runtime validator is [contract.py](../evaluation/schemas/contract.py).
[case.schema.json](../evaluation/schemas/case.schema.json) is generated from its
strict Pydantic Case model. Nested objects reject extra fields. Cross-file,
taxonomy, policy and family constraints require `validate_bundle`, not JSON Schema
alone. Every field is required; nullable values must be explicit.

| Field | Meaning |
| --- | --- |
| id | Unique lowercase evaluation case ID, not a production task ID |
| family_id | Structural family; checked against the family registry and computed input signature |
| version | Strict integer 1; boolean is rejected |
| split | `development` or `frozen_evaluation` |
| categories | Nonempty unique labels from the closed evaluation category vocabulary |
| evidence_level | `component_fixture` in A; never a live-cloud claim |
| supported | Request mode is within existing GET/POST page-number scope; NOT an end-to-end verification result |
| expected_outcome | `success`, `expected_rejection`, or `controlled_failure` |
| fixture | Public-input ref, fixture ID and generator version |
| request | Same public-input ref and observed method; no oracle/solution |
| oracle | Reference to a scorer-only oracle document |
| retrieval_labels | Reference to external relevance labels |
| failure_expectation | Terminal classification, allowed codes, phase, exception type, maximum execution requests on failure |
| repair_expectation | Trigger, authoritative policy disposition, eligibility, permission, expected application and budget |
| provenance | Authored source, natural_failure=false, injection marker/type and limitation note |
| hashes | Canonical hashes of fixture, oracle and labels |

`supported=true` is intentionally an applicability property of this NEW evaluation
schema, not the frozen benchmark's `expected.supported` field. No benchmark field
is changed. Component fixture verification does not establish observation,
cloud planning, export or delivery success.

## Expected outcomes and provenance

- `success`: scorer expects a correct, complete output. The pointer-applied case
  assumes the explicitly injected missing-items-pointer plan, not a natural LLM error.
- `expected_rejection`: a rejection/error is the desired contract result. It is
  excluded from ordinary task-success/failure-rate denominators.
- `controlled_failure`: a deliberate bad-plan case remains unresolved; a matching
  failure validates that case contract, not task completion.

All cases are authored synthetic assets. Four drift fixtures use response-level
injections; two pointer fixtures use `missing_items_pointer`; cursor/offset use
`unsupported_page_plan`. None claims a naturally occurring model failure.

The cursor/offset cases test an explicit plan using an unobserved `page` field.
Current `validate_pagination` raises plain ValueError on that path; `classify`
returns UNCLASSIFIED, not the registered `unobserved_page_parameter` spec.
Thus `allowed_codes=[]`, `exception_type=ValueError`, `phase=unknown`; the oracle
stores no invented error code. These cases do NOT prove automatic rejection of
every cursor/offset interpretation and do NOT implement cursor/offset execution.

`failure_expectation` describes the terminal failure. A successfully repaired
case has no terminal failure, while its initial trigger remains in
`repair_expectation.trigger_code`. `may_apply` is policy permission; it does not
claim a candidate exists. Ambiguous candidates may have permission but
`expected_applied=false`. `max_execution_requests` is only a failure-path ceiling,
not a task resource measurement.

The five development cases are one envelope family, including all four integrity
mutations. They are not advertised as five independent structures. Pointer
applied/ambiguous variants also stay together. Counts are not statistical sample
independence claims.

The structural signature uses method, continuation kind, query presence,
endpoint count and normalized first-response shape. It ignores URL, request ID,
key spelling, record values and multiplicity of identical member shapes. Sensitive
keys are excluded using the existing SENSITIVE definition, so adding a canary
cannot manufacture a new family. Equivalent signatures cannot cross splits even
when family IDs differ. Case family signatures must match their registry entry.

This conservative signature catches simple renaming; it is not a complete semantic
similarity detector. Human structural review remains a B acceptance requirement.
The A split is a schema acceptance sample, not an untouched statistical holdout:
its answers are inspected by these authoring tests. Final blind evaluation requires
fresh family-held cases and explicit exposure tracking. Do not describe A authoring
checks as an independent model comparison.

## Oracle and scoring contract

Oracles are separately authored, not inferred from retrieval results. For success:
records, exact page/record count, output schema, unique key, completeness and result
hash are required. Failure oracles must not fabricate successful records or counts;
their terminal classification must match the case expectation.

Result canonicalization preserves array order. The current fixtures require exact
record order and exact types (boolean is not integer). Completeness must be `complete`.
No approximate float equality, record reordering or hidden normalization is used.

`score_task_result(report, records, oracle, collector=None)` requires:

```text
status succeeded AND exact output hash AND schema AND unique key validity
AND uniqueness AND record count AND page count AND complete
```

It returns separate task_success and delivery_success. Delivery additionally requires
all three existing collector flags to be true AND an independently checked collector
result with matching items, pages and completeness. Flags alone are insufficient.
Tests cover failed state, wrong count/page/value/type, duplicates, absent evidence,
partial output and collector flags without collector evidence.

`score_expected_rejection` checks failed state, the specified code/phase (or the
explicit unclassified exception expectation), and an observed request count within
the failure ceiling. Unknown request count cannot pass. Its boolean is a rejection
contract score, never the numerator of task_success_rate.

`score_retrieval` accepts only ranked IDs and external relevant IDs. It reports
top1_hit, top2_hit and MRR@2 because the current retriever returns at most 2 cases.
No relevant labels means N/A (None), not zero. Duplicate retrieved IDs and more than
two results are rejected. A/B groups are not marked miss merely because their
output omits failure_modes. For failure-code relevance use the separate external
failure_relevant_case_ids with the same pure scorer. These helpers do not aggregate
runs, call services, access files or write databases.

## Retrieval corpus

Six authored cases share identical ordered IDs, titles, terms and guidance in all
three variants. E1 has only text fields; E2 adds features; E3 adds failure_modes
and repairability while retaining exactly the E2 features. The bundle validator
checks both identity and metadata differences, plus external label references.

Knowledge definitions are validated by the existing knowledge loader. Error codes
come from errors.SPECS; dispositions come from project_repairability and the existing
repair constants. No independent policy registry is created. Evaluation corpora are
not wired into production retrieve, fields, prompts or diagnostics.

No comparative retrieval quality or success-rate claim is made in A. This corpus is
small and curated; B must broaden independent relevant and no-answer queries without
editing titles/terms/guidance differently between ablation groups.

## Hash contract

JSON canonical bytes: UTF-8, sorted object keys, separators `,` and `:`,
ensure_ascii=false, allow_nan=false. Array order remains semantic. Duplicate keys
and nonfinite JSON values fail closed. Formatting and physical CRLF/LF do not
change logical JSON hashes; newline characters inside string values remain data.

Every case, input, oracle, label, corpus and published schema is indexed in
manifest.files by canonical SHA256. Each case additionally hashes its dependencies.
manifest.sha256 hashes the complete manifest. The manifest does not hash itself,
so there is no circular hash definition. Five evaluation Python sources, including
the builder, are hashed after normalizing physical CRLF to LF. A source mismatch,
missing dependency, unindexed JSON or changed ablation identity fails validation.

Source text hashes are checkout-portable, not runtime-environment hashes. The
generated Pydantic schema is tied to the current dependency version; environment
locking remains M6.2 work.

Read-only validation from repository root:

```powershell
.venv/Scripts/python.exe -B -c "from pathlib import Path; from evaluation.schemas.contract import validate_bundle; print(len(validate_bundle(Path.cwd())))"
```

The builder's build_assets returns a mapping of relative paths to deterministic
UTF-8 text, reading only its source files for identity. It never runs retrieval,
the Agent, a model or a service. Its CLI refuses to overwrite differing existing
assets, before doing any writes. A authoring corrections were made before human
acceptance; they are not changes to a frozen dataset.

After m6-v1 dataset freeze, extensions use m6-v2/m6-v3; never overwrite m6-v1 to
improve a metric. A is not that final freeze.

## Canary and resource boundary

One synthetic secret sentinel exists only in the allowed raw input source. Public
projection uses the existing redaction contract. Static tests assert no sentinel
in planner-facing projection or other evaluation JSON. This is not evidence that
future prompts, logs, exported collectors or live evaluation artifacts are safe;
those paths require harness-level tests later.

All fixture responses are fixed, ordered and independent of clocks/randomness.
response_for is a pure ordinal lookup, not a GET/POST/cursor execution engine.
The component semantics tests call the existing validator, proposer and executor
with test-authored plans and MockTransport. CloudGateway and uncontrolled HTTP
transports are explicitly blocked in those tests. No formal runner, browser
observation, cloud planner, collector export or live socket server is introduced.
